## 1. Executive Summary

This document describes the current state of the toke training corpus, its composition, diversity characteristics, and proposed rebalancing targets. The corpus is being assembled to fine-tune a code-generation model (Qwen 2.5 Coder 7B via QLoRA) and retrain a dedicated tokenizer (SentencePiece BPE, 8K vocab) for the toke programming language. The goal is to pass Gate 2 evaluation criteria and demonstrate that an LLM can reliably generate correct toke programs.

**Current corpus:** 197,856 validated Phase 2 programs across 24 categories.
**Proposed target:** 150,000 programs after rebalancing for diversity.
**Key concern:** Mutation-derived entries dominate at 76.5%, masking low effective diversity.

---

## 2. What is toke?

toke is a statically typed, machine-native programming language designed primarily for reliable generation, repair, validation, and execution by large language models. It targets a unique design space: minimising token overhead in source representation while eliminating syntactic ambiguity.

**Key design goals:**
- Minimise token overhead in source representation
- One canonical form per construct (no equivalent alternatives)
- Deterministic backtrack-free parsing (bounded lookahead of up to 3 tokens) and type checking
- Machine-readable structured compiler diagnostics (stable error codes)
- Generate-compile-inspect-repair workflows without human interpretation
- Native binaries via LLVM, no runtime dependency
- Arena memory discipline (no GC)

**Phase 2 syntax profile** (normative default, frozen 2026-04-05):
- 59-character set: lowercase letters, digits, 18 symbols (`$@(){}:;=<>!+-*/.,"`)
- No uppercase letters, no square brackets, no underscore
- 12 keywords: `m`, `f`, `i`, `t`, `if`, `el`, `lp`, `br`, `let`, `mut`, `as`, `rt`
- Type sigil: `$` prefix for types (`$str`, `$int`, `$point`)
- Array sigil: `@` prefix (`@$int`, `@$str`)
- Return operator: `<` (angle bracket, not `return`)

**Example -- array sum:**
```
m=sum;f=sum(arr:@i64):i64{let total=mut.0;lp(let i=0;i<arr.len;i=i+1){total=total+arr.get(i);};<total};
```

## 3. Current Phase and Gate 2

### 3.1 Where We Are

The project follows a gated milestone structure. **Gate 1 PASSED on 2026-04-03**, demonstrating that the compiler, tokenizer, and a baseline fine-tuned model could produce compilable toke programs. Gate 2 is the next milestone.

### 3.2 Gate 2 Criteria

| Criterion | Threshold | Gate 1 Baseline |
|---|---|---|
| Pass@1 accuracy | >= 75% | 63.7% |
| Token reduction vs natural language | >= 15% | 12.5% (8K) / 13.1% (32K) |
| Compile rate on generated programs | >= 95% | TBD |
| Corpus size | >= 100,000 programs | ~47K at Gate 1 |
| Category coverage | >= 10 categories | 14 categories |
| Multi-tokenizer validation | >= 3 tokenizers | TBD |
| Gate 1.5 reproducibility | by 2026-05-03 | Pending |
| Error taxonomy | published | TBD |

### 3.3 Training Pipeline

The Gate 2 pipeline runs in four stages:

1. **Tokenizer retrain** -- SentencePiece BPE with 8K vocabulary, trained on the merged corpus JSONL. A dedicated tokenizer is essential because toke's 59-character set and compact syntax are poorly served by general-purpose tokenizers trained on natural language or conventional programming languages.

2. **Training data preparation** -- Corpus entries are converted to instruction-tuning format with 95/5 train/eval split. Each entry becomes a prompt-completion pair where the prompt describes the task and the completion is the toke source.

3. **QLoRA fine-tuning** -- Base model: Qwen 2.5 Coder 7B. LoRA adapters are trained on the instruction-tuned corpus. This approach keeps compute requirements manageable (single GPU) while leveraging the base model's code understanding.

4. **Pass@1 evaluation** -- 20 samples per task at temperatures 0.0 and 0.2. Programs are compiled with `tkc --check` and evaluated against reference outputs.

### 3.4 Critical Path

```
Corpus rebalancing (this review)
    -> Tokenizer retrain on final corpus
        -> Training data prep
            -> QLoRA fine-tuning
                -> Pass@1 evaluation
                    -> Gate 2 decision
```

The corpus composition directly determines what the model learns. Rebalancing before tokenizer retraining is the current blocker.

Sample COMPOSE-D program (4 functions, pipeline + accumulator pattern):
```
m=accAbs;
f=max(lhs:f64;rhs:f64):f64{
  let result=mut.0.0;
  lp(let i=0;i<1;i=i+1){
    if(lhs>rhs){result=lhs}el{result=rhs}
  };
  <result
};
f=abs(x:f64):f64{
  let temp=mut.0.0;
  if(x<0 as f64){temp=-x}el{temp=x};
  <temp
};
f=absMax(lhs:f64;rhs:f64):f64{<abs(max(lhs;rhs))};
f=accumulate(arr:@f64):f64{
  let r=mut.0.0;
  lp(let i=0;i<arr.len as i64;i=i+1){
    r=r+abs(arr.get(i as u64))
  };
  <r
};
```

#### Grammar-Fuzzed Programs

Randomly generated syntactically-valid programs from a top-down grammar walker. Type-aware, seeded for reproducibility. Max depth 6, up to 4 functions per module.

| Category | Count | Description | Unique Seeds |
|---|---|---|---|
| FUZZ | 9,099 | Grammar-generated random programs, 100% compile rate | 9,099 |
| **Subtotal** | **9,099** | | **9,099** |

These provide grammar coverage that LLM-generated programs may miss -- unusual but valid combinations of syntax that a human or LLM wouldn't naturally write.

#### Mutations -- Mechanical Transforms of Phase A Seeds

Semantic-preserving (or near-preserving) mutations of Phase A programs. Each mutation type applies a specific transformation and validates the result with `tkc --check`.

| Category | Count | Description | Est. Unique Seeds |
|---|---|---|---|
| MUT-variable_rename | 94,218 | Consistent variable renaming (e.g., `total` -> `acc`) | ~300 |
| MUT-let_to_mut | 33,538 | Promote immutable `let` to `let x=mut.val` | ~272 |
| MUT-constant_variation | 14,197 | Perturb numeric literals by +1 | ~145 |
| MUT-type_widening | 8,321 | Replace `i64` with `u64` where safe | ~235 |
| MUT-expression_extraction | 1,336 | Extract return sub-expressions into temp bindings | ~79 |
| **Subtotal** | **151,610** | | **~8,800** |

**Mutation strategies explained:**

1. **variable_rename** -- Renames local variables consistently using a candidate map. Teaches the model that variable names are arbitrary and the program's meaning is in the structure. Example: `let total=mut.0` -> `let acc=mut.0` with all references updated.

2. **let_to_mut** -- Adds unused mutability to immutable bindings. Teaches the model that `mut.` is valid on any binding, broadening its syntactic repertoire.

3. **constant_variation** -- Perturbs numeric literals by small amounts (skips 0, 1, -1). Creates programs that are structurally identical but compute different values.

4. **type_widening** -- Replaces signed integers (`i64`) with unsigned (`u64`) where no negative values appear. Teaches type flexibility.

5. **expression_extraction** -- Extracts complex return expressions into named temporaries. Teaches alternative ways to structure the same computation.

### 4.2 Diversity Analysis

| Metric | Value |
|---|---|
| Total validated entries | 197,856 |
| Total unique programs (est.) | ~50,000 |
| Mutation entries | 151,610 (76.5%) |
| Mutation unique seeds | ~8,800 (4.4% of total) |
| Non-mutation entries | 46,246 (23.4%) |
| Non-mutation unique seeds | ~46,200 (~100%) |
| Categories | 24 |
| Programs using stdlib imports | ~6,500 (3.3%) |
| Multi-function programs (2+) | ~14,000 (7.1%) |
| Single-function programs | ~184,000 (92.9%) |
| Average tk_tokens (non-mutation) | ~80 |
| Average tk_tokens (mutation) | ~45 |
| Longest program (DOC-EXP) | ~584 tokens |

**Key diversity concerns:**

1. **Mutation dominance:** 76.5% of entries are mutations of ~8,800 unique seeds. The model will see many trivial rephrasings of the same programs, with diminishing returns on learning.

2. **Single-function bias:** 92.9% of programs contain exactly one function. Real toke programs will need multiple interacting functions.

3. **Low stdlib coverage:** Only 3.3% of entries use stdlib imports. The model may struggle to generate programs using `std.file`, `std.str`, `std.math`, etc.

4. **Near-zero error handling:** Only 4 entries demonstrate error types, result types, or the `!` error propagation operator. This is a critical gap.

5. **Short programs:** Most entries are 1-3 lines of compact toke. The model may not generalise to longer, multi-module programs.

### 5.1 Error Triples

The largest untapped asset. Each entry contains:
- `broken_source`: A program with a deliberately injected error
- `diagnostic`: The compiler diagnostic produced
- `fixed_source`: The corrected program

Six injection types: type mismatch, missing semicolons, wrong operators, immutable reassignment, undefined variables, wrong argument counts.

The `fixed_source` field contains valid programs that are structurally similar to Phase A programs but with specific repair patterns applied. Validating these could add significant diversity, particularly for teaching the model about error-repair workflows.

### 5.2 Remaining Mutations

485,731 mutations remain unvalidated (offset 200K-685K). At the observed ~76% pass rate, this could yield ~370K additional entries. However, these derive from the same ~8,800 seed pool, so additional mutations provide volume without proportional diversity improvement.

## 6. Proposed Rebalancing

### 6.1 Target: 150,000 Programs

We propose 150K as the sweet spot:
- Well above the Gate 2 minimum (100K)
- Large enough for effective QLoRA fine-tuning of a 7B model
- Small enough to train in reasonable time on available hardware (Mac Studio M4 Max)
- Forces prioritisation of diversity over volume

### 6.4 Mutation Sampling Strategy

Rather than random sampling, we propose **seed-diverse sampling**: for each capped mutation category, select at most N mutations per unique seed program, prioritising seeds that are underrepresented. This maximises the number of distinct base programs the model encounters.

## 7. Open Questions for Reviewers

1. **Mutation ratio:** Is 62.5% mutations still too high? Should we cap more aggressively (e.g., max 3 per seed, bringing mutations to ~50K and total to ~100K)? Or is the volume valuable for the tokenizer even if diversity is limited?

2. **Error handling gap:** Only 4 error-handling programs exist. Should we invest in manual conversion of the 4,354 Phase 1 A-ERR entries, or generate new error-handling programs? This is a critical language feature with near-zero training coverage.

3. **Error triples:** Should we include both `broken_source` and `fixed_source` as separate training entries (teaching the model what NOT to do and how to fix it), or only the `fixed_source`?

4. **Program length:** 93% of programs are single-function, 1-3 lines. Should we invest in generating longer, multi-module programs? The COMPOSE-D entries average 4 functions and ~182 tokens -- should we target more of these?

5. **Stdlib coverage:** Only 330 original documentation examples exist, expanded to 6,216 via mutation. Should we generate more stdlib-using programs, or is the mutation expansion sufficient for the tokenizer to learn stdlib tokens?

6. **Corpus size vs diversity:** Would a smaller, more diverse corpus (e.g., 80K with no more than 2 mutations per seed) train a better model than a larger, less diverse one (150K with 5 per seed)?

7. **Fuzz programs:** The 9,099 fuzzed programs are syntactically valid but semantically meaningless (random variable assignments, unused values). Is this helpful for teaching grammar, or does it teach the model to generate nonsense?

8. **Target increase:** Should we validate more of the 485K remaining mutations and push the corpus to 200K+, accepting the reduced effective diversity? Or is 150K the right ceiling?

## 10. Appendix: Generation Methods

| Method | LLM Cost | Description |
|---|---|---|
| Phase A (LLM generation) | High | Task specs -> Claude/GPT -> toke programs. Highest diversity per entry. |
| Mechanical composition | Zero | Combine existing functions by type-matching signatures. |
| Grammar fuzzing | Zero | Random walk over toke EBNF grammar, type-aware. |
| Mutation engine | Zero | 5 semantic-preserving transforms on existing programs. |
| Error injection | Zero | 6 deliberate error types producing (broken, diagnostic, fixed) triples. |
| Documentation extraction | Zero | Extract code blocks from spec/stdlib docs. |
| Phase 1->2 conversion | Zero | Automated syntax transform + autofixer + compile validation. |
| EC2 domain generation | High | Domain-targeted LLM generation for 8 application areas. |
